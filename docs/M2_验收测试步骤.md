## 2. SQL Editor 业务功能验收（约 10 分钟）

> **先看这条**：SQL Editor 里没有登录用户（没有 JWT），所以 `get_app_state` 这类“需要身份”的函数会报 `请先登录`——这是正常的安全行为，不是脚本坏了。
> 解决办法：在 SQL Editor 里**模拟一个已登录的管理员**。每次 Run 前把下面这两行和要测的语句**一起粘贴执行**（Supabase SQL Editor 每次 Run 可能是新连接，所以每段都带上最稳）：

```sql
-- 2.0 模拟登录：把 admin 的身份塞进当前会话
select set_config('request.jwt.claims',
  (select json_build_object('sub', id::text, 'role', 'authenticated')::text
     from public.profiles where username = 'admin'), false);

-- 自检：应显示 admin 和 admin 的 uuid
select public.caller_role() as 当前角色, auth.uid() as 当前用户;
```

以下按顺序粘贴执行，每步看结果是否符合“预期”。

### 2.3 积分登记 + 2 秒冻结（重点）

**先说明为什么不再需要填 ID**：下面用子查询自己找记录，不用手抄 uuid。另外 SQL Editor 里**一次 Run 就是一个事务**，事务内 `now()` 不会走，所以“等 3 秒再改”必须分两次 Run 做——一次 Run 里 `pg_sleep(3)` 等再久都还是冻着。

**第 1 段（一次 Run 跑完）：登记一条 + 立刻尝试修改，观察被拒**

```sql
select set_config('request.jwt.claims',
  (select json_build_object('sub', id::text, 'role', 'authenticated')::text
     from public.profiles where username = 'admin'), false);

do $$
declare
  v_id uuid;
begin
  v_id := (public.add_record(
    (select id from public.students where student_no = 'T0001'),
    '加分', '学业表现', '冻结测试记录', 1, current_date) ->> 'id')::uuid;

  begin
    perform public.update_record(v_id, '立刻改', 2);
    raise notice '结论异常：2 秒内修改竟然成功了';
  exception when others then
    raise notice '记录 % 已被保护，拒绝原因：%', v_id, sqlerrm;
  end;
end $$;
```

预期（Messages 面板）：`记录 ... 已被保护，拒绝原因：该记录刚写入，处于 2 秒锁定中，请稍后再改`。

**第 2 段（隔 3 秒以后，单独 Run 一次）：改成别的分值**

```sql
select set_config('request.jwt.claims',
  (select json_build_object('sub', id::text, 'role', 'authenticated')::text
     from public.profiles where username = 'admin'), false);

select public.update_record(
  (select id from public.records
    where reason = '冻结测试记录' and status = '正常'
    order by created_at desc limit 1),
  '冻结后修改', 2) as 修改结果;
```

预期：成功返回记录 JSON（`reason` 变成“冻结后修改”，`points` 变成 2）。
若仍提示“2 秒锁定中”，说明两次 Run 间隔不到 2 秒，等几秒再跑这段即可（子查询会自动取最新那条）。

### 2.4 规则周期上限（重点）

**第 1 段：建一条“每周期最多 2 次”的规则（已存在就不重建）**

```sql

     from public.profiles where username = 'admin'), false);

do $$

  if not exists (select 1 from public.rules where reason = '验收上限规则') then
    perform public.admin_save_rule('{"score_type":"加分","category":"验收","reason":"验收上限规则","points":1,"limit_type":"count","limit_value":2,"sort_order":999}'::jsonb);
  end if;

select id, reason, limit_type, limit_value from public.rules where reason = '验收上限规则';
```

**第 2 段：连续登记 3 次，第 3 次应被拒**

```sql

  (select json_build_object('sub', id::text, 'role', 'authenticated')::text
     from public.profiles where username = 'admin'), false);

select public.add_record(
  (select id from public.students where student_no = 'T0002'), '加分','验收','上限测试1',1,current_date,
  (select id from public.rules where reason='验收上限规则' limit 1));

select public.add_record(
  (select id from public.students where student_no = 'T0002'), '加分','验收','上限测试2',1,current_date,

select public.add_record(

  (select id from public.rules where reason='验收上限规则' limit 1));
```

预期：整段 Run 报错，信息含 `规则「验收上限规则」本周期最多登记 2 次，已达上限，不能再登记`。

> 看到这个报错就说明上限生效了。整段会一起回滚（前两条也不会留下）——这是正常现象，因为三条语句在同一个事务里。所以这段**可以反复跑**，每次都会在第 3 条报错。

### 2.6 周快照 + 周结算（重点）

```sql
-- 造一个“刚刚到点”的周分隔点
-- period_key 取本周真实周键（如 2026-43），这样 current_week_key() 依旧正常；
-- 先清掉上一轮的同名测试分隔点，保证这段可以反复跑。
delete from public.weekly_summaries
 where boundary_id in (select id from public.boundaries where label = '验收测试周');
delete from public.boundaries where label = '验收测试周';

insert into public.boundaries(type, period_key, boundary_at, label, is_manual)
values ('week', to_char((now() at time zone 'Asia/Shanghai')::date, 'IYYY-IW'),
        now() - interval '2 minutes', '验收测试周', true)
on conflict (type, boundary_at) do nothing;

select public.maybe_run_period_jobs();

select period_key, boundary_id, summary->>'effects_done' as effects_done, created_at
  from public.weekly_summaries order by created_at desc limit 1;

select count(*) as 周奖励次数行 from public.lottery_chances where chance_type='weekly_group';
select count(*) as 小组惩罚抽选 from public.lottery_draws where source='monthly_group_penalty';
```

预期：`maybe_run_period_jobs` 返回 `ok_count >= 1, fail_count = 0`；出现 1 条本周快照且 `effects_done = true`（它在 `summary` 里，用 `summary->>'effects_done'` 取）。

- **周奖励次数行**：前 3 名小组每人 +1 次。测试数据只有 2 个组（验收一组、二组），两组都在前 3 名，所以人数 = 你建的学生数。
- **小组惩罚抽选 = 0 是正常的**：只有小组总数 ≥ 前 3 + 后 3 = 6 个组时才会给后 3 组抽惩罚；测试环境 2 个组不触发。真实班级有 6 个组，到点会自动抽。

### 2.7 月结算 + 自动抽选（重点）

```sql
-- 造一个“刚刚到点”的月分隔点（period_key 取本月真实月键，避免污染 current_month_key）
delete from public.settlements
 where boundary_id in (select id from public.boundaries where label = '验收测试月');
delete from public.boundaries where label = '验收测试月';

insert into public.boundaries(type, period_key, boundary_at, label, is_manual)
values ('month', to_char(now() at time zone 'Asia/Shanghai', 'YYYY-MM'),
        now() - interval '2 minutes', '验收测试月', true)
on conflict (type, boundary_at) do nothing;

select public.maybe_run_period_jobs();

select status, period_key, auto_draw_count, started_at, finished_at,
       jsonb_array_length(coalesce(summary->'reward'->'rows','[]'::jsonb))  as 奖励次数人数,
       jsonb_array_length(coalesce(summary->'penalty'->'rows','[]'::jsonb)) as 惩罚次数人数
  from public.settlements order by created_at desc limit 1;

select count(*) as 自动抽选条数   from public.lottery_draws where source='auto';
select count(*) as 剩余未用奖励次数 from public.lottery_chances where pool_type='reward'  and used_count < amount;
select count(*) as 剩余未用惩罚次数 from public.lottery_chances where pool_type='penalty' and used_count < amount;

-- 结算会开启 30 分钟维护模式，测试完手动关掉，避免影响后面的测试
update public.app_config set maintenance_until = now() - interval '1 minute' where id = 1;
```

预期：`settlements.status = done`；`auto_draw_count` 等于本月未用次数（月结算会把它们全部自动抽掉）；`lottery_draws` 出现 `source='auto'` 记录；**最后两个“剩余未用”都应为 0**（已自动抽完）。奖励/惩罚次数按公式生成：奖励 = max(月加分÷10, 月加分前 15 名给 1)，惩罚 = 月扣分÷5 + 第二类。

> 注意 `settlements` 表没有 `rows` 列，次数明细在 `summary` jsonb 里的 `reward.rows` / `penalty.rows`，上面用 `jsonb_array_length` 取人数。

## 9. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| SQL Editor 报 `请先登录`（P0001） | 正常：SQL Editor 没有登录身份（无 JWT）。按第 2 节开头的“2.0 模拟登录”把 admin 身份塞进会话再调用，或直接用第 3 节的 REST 脚本 |
| 报 `学号「T0001」已被其他学生使用` | 2.2 已经成功建过这批测试学生（重复执行会撞学号）。直接跳过 2.2，或换学号，或用 2.2 里的清理 SQL |
| 2.3 第 2 段仍提示“2 秒锁定中” | 两次 Run 间隔不到 2 秒（SQL Editor 每次 Run 是独立事务，但人点得太快）。等几秒再跑同一段即可 |
| 2.4 整段报错后查询发现一条记录都没留下 | 正常：整段 Run 是一个事务，第 3 条报错会连带回滚前两条；报错本身就是“上限生效”的证据 |
| `function public.current_week_key() does not exist` | 用了旧版脚本；重新 build 或直接用仓库里最新的 `schema.sql` |
| `permission denied for table app_config` | 正常：前端不允许直读配置，必须走 RPC（如 `get_app_state`） |
| SQL Editor 里调用 RPC 一切正常，前端却提示没权限 | 前端身份来自登录 JWT；检查是否已登录、`profiles.status` 是否 `active` |
| 结算后记不了分 | 月度结算开启了 30 分钟维护模式；等结束或 `update public.app_config set maintenance_until = now() - interval '1 minute' where id=1;` |
| 学生登录提示邮箱不存在 | 学生账号用户名=学号（小写），登录邮箱是 `学号@banji.local` |
| 迁移后老记录点“编辑”报错 | 老记录 `record_date` 不是 `YYYY-MM-DD`，按第 4 步第 5 小节的 SQL 查出来修正 |
| 迁移时提示外键/类型错误 | 十有八九是线上表结构与 V1.6 schema.sql 不一致；把报错原文发我，先跑备份恢复 |
