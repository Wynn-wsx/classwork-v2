## 一、需求口径（已确定）

### 1. 奖惩抽选层（手写需求二 + 2026-10-24 澄清）

| 事项 | 确定口径 |
|---|---|
| 奖励抽选次数 | **当月累计加分每满 10 分得 1 次**（floor，如 +23 分得 2 次） |
| 惩罚抽选次数 | **当月累计扣分每满 5 分得 1 次**（floor，如 -12 分得 2 次） |
| 第二类 | 月结算时，**当月净积分全班倒数十名**的学生 |
| 第二类的惩罚 | 每人**额外 1 次**惩罚抽选 |
| 第二类的奖励 | 第二类学生**不获得**奖励抽选。口径（2026-10-24 再确认）：**未使用的奖励次数不做"作废"动作**（不生成作废记录、不占仓库、不自动抽），随月度清零自然归零；**仅在该月月度汇总中把其奖励抽选标记为"作废"**；已抽走的奖励不追回 |
| 次数周期 | 每 1 个月清零一次，**上月积分不参与**本月换算（以月分隔点划界） |
| 清零时点 | 与「月分隔点」同一时刻 |
| 清零动作 | 暂停服务 30 分钟；对当月**未使用的次数自动抽选** |
| 奖池 | 奖励池、惩罚池为**两个独立池子** |
| 抽选结果 | 做成**仓库**形式：每次抽选有记录、有**有效期**，详细规则后续定义 |
| 实现方式 | Supabase 数据库 **pg_cron 定时任务**到点执行结算 |

### 2. 数据库时间规则（手写需求三）

1. 业务时区统一为**东八区（Asia/Shanghai，UTC+8）**，国际通用计时；数据库存 `timestamptz`，界面按北京时间展示（沿用现有 `fmtBeijingTime`）。
2. **登记时间限制器**，同时拦截两类非法登记：
   - **未开放时间**：登记日期晚于系统当前时间（未来时间）；
   - **已冻结时间**：登记日期落在已结束（已冻结）的登记月。
3. 管理员设置**周分隔点、月分隔点**，隔开相邻的登记周、登记月；配置方式为**规则自动生成 + 可手动增删改**（如节假日顺延）。
4. 过去的登记月自动冻结。
5. 登记周期内可设**积分规则更新点**。

### 3. 数据库规则（手写需求四 + 澄清）

1. **每条积分记录在一次写入操作后冻结 2 秒**，冻结期间该**本条记录**不可被修改/删除（只锁本条，不锁该学生其他数据）。
2. 规则更新点的含义（已澄清）：每个周期内，**部分加扣分项目设有次数/分数上限**，登记不得超出上限；规则更新点**重置这些计数**，为下一周期做准备。
3. **默认每个周分隔点就是一个规则更新点**，另支持管理员额外新增自定义更新点。
4. 规则更新点只重置「上限计数」，**不清零积分**。

## 二、总体技术方案

### 1. 关键架构改动：积分记录写入收敛到 RPC

现状：前端通过 PostgREST 直接对 `records` 表 insert/update/delete，RLS 只校验角色与小组。

新需求中的「时间限制、2 秒冻结、规则上限」都是**可绕过前端的业务规则**，必须在数据库端强制执行（符合 `development.md` 第 4 节"安全边界在数据库"）。RLS 策略表达不了这么复杂的多表校验，因此：

- 新增 3 个 `security definer` RPC：`add_record()` / `update_record()` / `delete_record()`，内部完成全部校验；
- 撤销 `records` 表对 `authenticated` 的直接 INSERT/UPDATE/DELETE 权限（保留 SELECT），写操作只能经 RPC；
- RPC 内继续校验角色（admin/executive/group_recorder）与小组范围（记录员只能写本组）；
- 备份恢复 `restoreBackup` 改为走 admin 专用 RPC（管理员恢复数据时不受时间/上限限制，但留痕）。

### 2. 周期与分隔点模型

- `app_config`（单行配置）：周分隔规则（星期几 + 时刻）、月分隔规则（几号 + 时刻）、维护窗口分钟数（默认 30）。
- `boundaries`（分隔点实例表）：按规则**预生成未来 12 个月**的全部周/月分隔点；每条可手动增删改。
  - `type = 'month'`：月分隔点（同时也是规则更新点）；
  - `type = 'week'`：周分隔点（默认规则更新点）；
  - `type = 'rule_update'`：管理员额外新增的自定义更新点。
- 登记月归属：用 `record_date` 落在相邻两个月分隔点之间的区间判定，写入时由 RPC 计算并冗余存 `period_key`（如 `2026-10`）。
- 冻结判定：`record_date` 所属登记月的结束边界已过 → 已冻结；`record_date` > 当前业务日期 → 未开放。

### 3. 月度结算与 pg_cron（已确认采用）

- 事实（已查证）：pg_cron 在 Supabase 所有项目（含免费版）**默认启用**，可在 SQL Editor 用 `cron.schedule` 创建，作业以数据库内部权限运行 SQL/函数（来源：Supabase 官方文档 https://supabase.com/docs/guides/cron ；2026 年第三方指南称免费/Pro/Team 均默认可用）。
- 为兼容"分隔点可手动调整"，**不把 cron 写死在每月某日**，而是注册一个**每 10 分钟运行一次的检查作业** `maybe_run_monthly_settle()`：
  - 查 `boundaries` 中是否存在 `boundary_at <= now()` 且未结算的月分隔点；
  - 用 `pg_advisory_lock` 防并发重入；结算进度写入 `settlements` 表。
  - （经验判断：10 分钟轮询对班级场景误差可接受；若要严格准点，可在每次手动调整分隔点后，用 `cron.alter_job` 或一次性 `pg_cron` 作业精确调度——列为可选项。）
- 结算流程（单个事务函数 `monthly_settle(p_boundary_id)`）：
  1. 写维护标志 `maintenance_until = boundary_at + 30 分钟`；前端进入即显示"月度结算中，预计 HH:MM 恢复"，期间全站只读；
  2. 汇总刚结束登记月每人净积分，倒数十名生成第二类名单（快照存 `settlements.second_class`）；
  3. 第二类学生：其剩余奖励次数**不自动抽、不生成作废记录**（随清零自然归零），仅在月度汇总快照中将其奖励抽选标记为"作废"；各加 1 次惩罚抽选，与其他人一起走第 4 步的惩罚自动抽选；
  4. 除第二类学生的奖励次数外，所有人剩余未用次数：从对应池子随机抽选（加权随机），生成 `lottery_draws`，`source='auto'`；
  5. 写 `settlements.status='done'`；`maintenance_until` 到点后前端自动解除（无需另排解锁作业）。
- cron 调度时间注意：pg_cron 默认按 UTC，表达式需按东八区换算或显式指定时区（`cron.schedule(name, expr, 'Asia/Shanghai', sql)` 4 参数形式），交付 SQL 时处理。

### 4. 规则上限机制

- `rules` 表增加：`limit_type`（none/count/points：不限/按次数/按累计分值）、`limit_value`（上限值）。
- `records` 表增加 `rule_id`（登记时带出规则，便于精确统计）。
- 计数方式：**实时统计**（不另建计数表，避免记录改删后计数失真）——RPC 写入前统计"当前规则更新点周期内，该规则的有效记录数/分值合计"，超限即拒绝。
- 当前周期起点 = 不晚于当前时间的最近一个 week/rule_update/month 分隔点（月分隔点也重置上限，见待验证项 11，先按此实现）。

### 5. 抽选次数与仓库

- 次数不建物化表，**实时计算**（保证记录修改/删除后次数一致）：
  - 应得奖励 = floor(周期内累计加分 / 10)；应得惩罚 = floor(周期内累计扣分绝对值 / 5)；
  - 已抽次数 = `lottery_draws` 中该周期该池的记录数；
  - 剩余 = 应得 − 已抽（作废的奖励次数在结算时以作废记录冲抵）。
- 月中第二类尚未产生：月中所有人先正常获得奖励次数并可正常抽选；月末结算时第二类学生**已抽的不追回**，**未使用的奖励次数不自动抽、不记作废**，随清零自然归零，仅在月度汇总快照中标记其奖励抽选"作废"（汇总字段 `reward_forfeit`）。
- `lottery_items`（奖/惩池条目，两池共用一表，`pool_type` 区分）：标题、说明、权重、是否启用、有效期规则（抽中后 N 天有效 / 固定到期日 / 永久）。
- `lottery_draws`（抽选记录=仓库）：学生、池类型、抽中条目快照、周期、来源（手动/自动）、抽选人、抽中时间、**到期时间**、状态（生效中/已过期/已作废）。

### 新增 RPC 一览

| 函数 | 作用 | 权限 |
|---|---|---|
| `add_record(...)` | 登记：校验时间限制、规则上限、写 frozen_until=now()+2s、period_key | 登录用户（记录员限本组） |
| `update_record(...)` | 修改：校验冻结月、2 秒冻结、上限 | 同上 |
| `delete_record(...)` | 软删除：校验冻结月、2 秒冻结 | 同上 |
| `admin_restore_records(jsonb)` | 备份恢复批量写入（旁路时间/上限，留痕） | 仅 admin |
| `get_period_state()` | 返回当前周期、是否冻结、maintenance_until、各更新点 | 登录用户 |
| `admin_save_separator_rules(...)` | 保存周/月分隔规则并重算未来分隔点 | 仅 admin |
| `admin_add_boundary / admin_delete_boundary` | 手动增删分隔点/更新点 | 仅 admin |
| `draw_lottery(student_id, pool_type)` | 手动抽选：校验剩余次数、维护期、权限、随机抽条目、写仓库+有效期 | 登录用户（记录员限本组） |
| `list_lottery_chances(period_key)` | 每人应得/已抽/剩余次数（供前端展示） | 登录用户 |
| `admin_save_lottery_item / toggle / delete` | 池子条目管理 | 仅 admin |
| `monthly_settle(boundary_id)` | 月度结算（事务、幂等、advisory lock） | cron / admin |
| `maybe_run_monthly_settle()` | cron 每 10 分钟调，发现到期分隔点则结算 | cron |

### RLS 概要

- `app_config` / `boundaries` / `settlements` / `lottery_items`：登录可读；仅 admin 可写（写操作多走 RPC）。
- `lottery_draws`：admin/executive 读全部；group_recorder 读本组；禁止直接写，仅 RPC。
- `records`：SELECT 策略不变；收回直接写权限。

## 六、待验证内容（需要你后续决定，先用建议默认值推进，不阻塞数据库骨架）

1. **倒数十名并列**：若第 10 名并列多人，建议**同分并列都算第二类**（沿用现有"同分同名次"规则，第二类可能 >10 人）。
2. **班级不足 10 人**：第二类是全部学生还是不设？建议全部计入倒数十名（即实际人数）。
3. **惩罚次数叠加**：扣分满额次数 与 第二类 1 次是否叠加？建议**叠加**（手写原文为"或"，指两条触发路径任一成立即有惩罚，满额可多次、第二类再 +1）。
4. **第二类已抽奖励**：✅已确认（2026-10-24）——月中已抽的奖励**不追回**；未使用的奖励次数**不做作废处理**（不生成作废记录、不自动抽），随清零自然归零；**仅在该月月度汇总中把其奖励抽选标记为"作废"**（`summary.reward_forfeit` 统计）。
5. **抽选操作人**：当前系统只有老师/记录员账号、没有学生账号。抽选是**老师/记录员代抽**（记录员限本组），还是需要新增学生账号？建议先做代抽。
6. **奖池/惩池条目清单与有效期**：需要你提供具体条目（如奖励"免一次值日""优先选座位"，惩罚"擦黑板一周"等）及各自有效期；骨架先建好，条目可随时录入。
7. **自动抽选时池子为空**：建议落一条"本期奖池为空，未抽中"记录，不补抽；待你确认。
8. **冻结月纠错通道**：冻结后发现记错怎么办？建议保留 **admin 专用纠错 RPC**（可改已冻结月，但强制留痕），记录员不可改。
9. **30 分钟维护期**：建议全站只读 + 维护提示，不允许任何写操作。
10. **上限粒度**：每条规则单独配置"次数上限"或"分值上限"，不启用的规则留空。是否符合你的设想？
11. **月分隔点是否同时重置规则上限**：建议是（新月即新周期）。
12. **pg_cron 轮询精度**：建议每 10 分钟检查一次，自动抽选实际触发时间可能晚于分隔点最多 10 分钟；若要求准点，改为每次调整分隔点后注册精确一次性作业（实现更复杂）。

## 七、风险与限制（如实说明）

- **我无法直接操作你的 Supabase 控制台**：M2/M3 的 SQL 需要你在控制台 SQL Editor 执行（我会给完整可重复执行的脚本和逐步说明）；前端可在本地直接连线上库验证。
- **线上库变更需先备份**：按 `development.md` 要求，执行迁移 SQL 前先导出 JSON 备份；建议先在 Supabase 新建一个测试项目跑通，再动线上。
- pg_cron 免费版默认可用这一点已查证官方文档，但**仍建议你在控制台实测** `create extension if not exists pg_cron;` 与一次 `cron.schedule` 测试作业（免费版作业并发与运行时长有上限，本方案作业为每 10 分钟一次的轻量 SQL，远低于限制）。
- 现有"无实时同步"技术债不变：月度结算若在某人页面停留期间发生，其本地内存不刷新，维护拦截依赖下次请求；结算以数据库结果为准。
- 纯前端单文件继续保持，不引入框架/构建；抽选动效用原生 CSS/JS 实现。
