# V2.0 数据库升级与部署说明

> 适用版本：V1.6 → V2.0.0（数据库层）
> 脚本位置：`开发文件/supabase/`（由 `_build/build_sql.py` 从模块生成，请勿手改成品）
> 本文只讲**数据库**怎么上线；前端与 cron 作业细节见各自模块说明。
> 想先自己验一遍脚本是否正常：照 [M2_验收测试步骤.md](M2_验收测试步骤.md) 走，含结构自检、功能验收、REST 端到端与升级/回退演练。

---

## 一、这次要交付的文件

| 文件 | 用途 | 说明 |
|---|---|---|
| `migration_v2.0.sql` | **线上库升级用**（V1.6 → V2.0） | 全量幂等脚本，推荐用它 |
| `schema.sql` | 新项目初始化 / 重跑修复用 | 内容与迁移脚本一致（全部幂等），空库也能一次建好 |
| `rollback_v1.6_policies.sql` | 应急回退 | 只恢复 V1.6 的读/写权限与角色函数，**不删 V2 的表和函数**，数据不动 |
| `_build/` | 源码模块 + 构建/校验脚本 | 内部开发用，**不要交付给学校/家长**；改脚本要改这里再 `python build_sql.py` |

两个脚本都是**可重复执行**的：建表 `if not exists`、加字段 `if not exists`、函数 `create or replace`、策略先 `drop` 再建、种子数据 `where not exists`。所以中途失败、执行两遍都安全。

## 二、执行前必须做的备份（重要）

1. **Supabase 自带备份**：控制台 → `Database` → `Backups`，确认最近的自动备份时间；免费版只有 7 天，升级前可手动触发一次。
2. **业务数据备份**：用 V1.6 前端「数据导出」（Excel/JSON）各导一份，存本地。这是最直观、最容易恢复的一份。
3. **建议先在测试项目跑一遍**：Supabase 免费可再建一个项目，把 `migration_v2.0.sql` 跑完、登录看一圈，再动线上项目。

## 三、执行步骤（线上项目）

1. 控制台 → `SQL Editor` → `New query`。
2. 打开 `开发文件/supabase/migration_v2.0.sql`，**全选 → 粘贴 → Run**。
   - 文件约 250 KB / 1.2 万行，`SQL Editor` 一般能一次跑完（约 10–60 秒）。
   - 若提示超时或编辑器卡住：按文件里的 `-- ==== 第N部分 ====` 分段标记，**从上到下**分批粘贴执行；因为全部幂等，分几次跑结果一样。
3. 看到最后一张统计表即为跑完，对照下面的“期望结果”核对。
4. **设置第一个超级管理员**（新库会自动建 `guanliyuan`，线上老库不会自动提权，必须手动做一次）：
   ```sql
   -- 把你自己要用的账号提升为超级管理员（用户名改成实际的：admin / banzhang / tuanzhishu ...）
   update public.profiles set role = 'super_admin' where username = 'admin';
   ```
   之后在系统「用户管理」里就能建老师账号、改分隔点规则、导出全量备份等（A1/A2/A8/B1/B3/B4/B7/B8/C1 均只属于超级管理员）。
   > 如果你希望保留班主任为普通 `admin`、另建一个 `guanliyuan` 超级管理员：
   > ```sql
   > select public.admin_create_user('guanliyuan', '请改成强密码', '管理员', 'super_admin', null);
   > ```
5. 登录前端验证：能登录、能看积分、能登记一条测试记录（登记后 2 秒内改不动属正常）。

### 升级后额外自检一条（历史数据格式）

V1.6 的积分记录日期是文本，V2.0 仍按文本存储，但新代码按 `YYYY-MM-DD` 解析。执行下面这条查询，**结果应为 0 行**：

```sql
select id, record_date, reason from public.records
 where record_date !~ '^\d{4}-\d{2}-\d{2}$'
 limit 50;
```

- 有结果说明历史记录日期不是标准格式（例如 `2026/9/15`、`2026年9月15日`）。这些老记录在 V2.0 里**不能直接编辑**（编辑会提示日期不合法），但会计入查询统计的前提是格式正确。
- 处理办法：把结果发给开发，按实际格式批量修正（如 `update public.records set record_date = replace(record_date,'/','-') ...`，改前先备份）。

## 四、定时作业（pg_cron）——周/月自动结算

V2.0 的周快照、月结算、自动抽选、未结算补偿都靠一个轮询作业，**必须配置**，否则到点不会自动结算。

### 1. 启用 pg_cron 扩展
控制台 → `Database` → `Extensions` → 搜索 `pg_cron` → 打开（Enable）。

### 2. 创建作业（SQL Editor 执行一次）
```sql
-- 每 10 分钟检查一次：有到点未处理的周/月分隔点就执行快照/结算
select cron.schedule(
  'banji_period_jobs',            -- 作业名（固定，重复执行会更新而不是重复建）
  '*/10 * * * *',                 -- 每 10 分钟
  $$select public.maybe_run_period_jobs();$$
);
```
- 时区：`pg_cron` 跑在 UTC 下，但 `maybe_run_period_jobs()` 判断的是数据库里的 `timestamptz`，与东八区配置无关，**不需要额外换算**。
- 想改成准点（如每天 00:00 整）：`'0 16 * * *'`（UTC 16:00 = 北京 00:00）。精度 10 分钟内对班级场景足够。

### 3. 验证
```sql
-- 看作业是否存在
select jobid, jobname, schedule, command, active from cron.job;

-- 手动跑一次（等价于 cron 触发；幂等，可随时跑）
select public.maybe_run_period_jobs();

-- 看最近执行结果
select jobid, status, return_message, start_time
  from cron.job_run_details order by start_time desc limit 10;

-- 看结算记录
select period_key, status, started_at, finished_at, auto_draw_count
  from public.settlements order by started_at desc limit 10;
```

### 4. 暂停 / 删除作业
```sql
select cron.unschedule('banji_period_jobs');   -- 删除
-- 或临时停用：update cron.job set active = false where jobname = 'banji_period_jobs';
```

## 五、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 执行报 `function public.current_week_key() does not exist` | 早期版本函数顺序问题 | 已在 `00_header.sql` 加 `set check_function_bodies = off;` 修复，用最新脚本即可 |
| 执行报 `permission denied for schema extensions` | 扩展 schema 权限 | 在 SQL Editor 用 postgres 角色执行（默认就是），不要用 anon/service 连接串 |
| 前端登录后一片空白 / 报 `permission denied for table profiles` | 前端还是 V1.6 旧文件 | 先部署 V2.0 前端 `index.html`，或临时执行回退脚本 |
| 积分登记提示“该记录已冻结” | 写后 2 秒保护 | 等 2 秒再改；确实要改走管理员冻结月纠错（C4） |
| 登记提示“已超出本周期上限” | 规则周期上限生效 | 管理员在「积分规则」里调 limit_value，或该规则本周期确实已满 |
| 到点没有自动结算 | pg_cron 没开/作业没建/作业被停用 | 见上面第四节；也可手动 `select public.maybe_run_period_jobs();` |
| 月结算失败，前端一直维护中 | 结算抛错，`settlements.status='failed'` | 看 `select * from public.settlements where status='failed'`，修数据后由超级管理员 `select public.admin_resettle('<boundary_id>');` |
| 没有任何超级管理员，用户管理用不了 | 线上老库不会自动提权 | 执行第三节第 4 步的 `update public.profiles ...` |

## 六、回退方案

如果 V2.0 上线后出现严重问题、需要临时回到 V1.6 前端：

1. 把前端 `index.html` 换回 V1.6 版本（基线包里有）。
2. SQL Editor 执行 `rollback_v1.6_policies.sql`：
   - 恢复 `auth_role()` / `auth_group()`；
   - 恢复 V1.6 的 RLS 策略与前端直写权限；
   - **不删** V2.0 的表、函数、数据（随时可再切回 V2.0）。
3. 如需重新启用 V2.0：把 `schema.sql` 再跑一遍即可（全幂等）。

> 注意：回退只回退“权限与前端”，不会把 V2.0 期间产生的业务数据抹掉；V2 期间建的学生账号、抽选记录都还在。

## 附：如果项目开启了 safeupdate（裸 DELETE 报 21000）

部分 Supabase 项目开启了 `pg_safeupdate` 保护，函数里不带 `WHERE` 的 `DELETE` 会报
`ERROR: 21000: DELETE requires a WHERE clause`。

V2.0 交付版已把这类语句改为 `DELETE ... WHERE true`（行为不变）。已部署旧版的库执行一次
`开发文件/supabase/patch_safeupdate.sql` 即可修复（幂等，可重复执行）。

## 附录 K：V2.0.10 月度惩罚次数规则（2026-10-25）

已部署 V2.0.9 的项目执行 `supabase/patch_v2.0.10_月度惩罚次数规则.sql`（幂等，只重定义 `public.monthly_settle(uuid)`，不动表结构和数据），随后 `notify pgrst, 'reload schema';`。

规则变化：按排名惩罚（后 N 名）由「扣分惩罚 + 1 次」改为「基础次数 = max(floor(扣分 ÷ 5), 1)」，并**允许 1 次奖励抵消 1 次惩罚**——当月加分达到奖励阈值（加分 ÷ 10 ≥ 1）时，基础次数 −1（最低 0）；未达奖励阈值（如 +6、−3 分）则照常记 1 次。补丁只影响**之后**的月结算；已结算月份的历史数据不自动重算，如需按新规则重算，用「周期汇总 → 月度结算 → 选择该月 → 重新结算该周期」。

## 附录 L：V2.0.11 需求批（抽选周期 / 手动发卡）

适用于已经部署 V2.0.10 的数据库，二选一：

- 只打补丁：在 SQL Editor 执行 `supabase/patch_v2.0.11_抽选周期与手动发卡.sql`（幂等，可重复执行）；
- 全量重建：执行最新 `supabase/schema.sql`（幂等）。

执行后务必刷新接口缓存：

```sql
notify pgrst, 'reload schema';
```

自检（应返回 2 行：`list_lottery_draws` 5 参数、`admin_grant_cards` 5 参数）：

```sql
select p.proname, pg_get_function_identity_arguments(p.oid) as args
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public'
   and p.proname in ('list_lottery_draws','admin_grant_cards')
 order by p.proname;
```

功能说明：
- 手动发卡仅 `super_admin`（管理员）与 `admin`（班主任）可调用；每次为每名学生各生成一张独立卡片（功能卡为「未使用」，星光卡/文本惩罚即时生效），并给本人发通知。
- 抽选周期下拉由 `list_lottery_draws` 的 `p_period_key`（`YYYY-MM`）控制，传 `null` 表示全部周期。
